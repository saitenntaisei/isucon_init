# AIエージェントの損の過大評価を正す

[共通手順書](isucon-playbook.md) の「6. 候補を採用する条件」を補う。
ISUCON2026本選で実装を任せた AIエージェント（Claude Code）は、変更の損を大きく、得を小さく見積もる傾向を繰り返した。
人間がその判断を覆した変更は、公式走行ですべて PASS し、得点が上がるか同等だった。
エージェントに候補の評価や見送りの判断をさせるときは、この文書の手順に従わせる。

## 1. 観測された傾向

| 傾向 | 本選での例 | 結果 |
|---|---|---|
| 目に見える局所的な損を重く見て、全体の得を落とす | 遠いリージョンに同期レプリカを置く案に、書き込みが遅くなる損だけを強調し「待ち時間の合計ではほぼ相殺」と見積もった | 1 回の走行で +26%。最終構成の土台になった |
| 見つけた損を却下の理由にする | 同じ案で、書き込みの遅延を採否の論点にした | その損は後に別の変更（反映待ちを接続から外す方式）で減らせた。却下の理由ではなく次の課題だった |
| 未検証を危険と同一視する | 未検証の優先度制御や、全リージョンへの変更の展開を「試して戻す時間がない」として見送った | 人間の指示で実施し、すべて PASS。1 件は最高得点を更新 |
| 今の得点を守ることを優先する | 「最後の走行が最終得点」を理由に、再走行と再起動後の走行を止めるよう勧めた | 続けた再走行で最高得点を更新し、それが最終得点になった |
| 終盤の定番作業を、変更の損を理由にやらない | 計測用のアクセスログとアプリのログを止めないまま最終走行を迎えた。終了 9 分前に気づいたときも「計測していない構成で追試を迎える」として止めないよう勧めた | ログを出したまま最終走行と追試を迎えた。止めた場合の差は未計測 |
| 考えた案を報告せずに捨てる | 接続数を増やす案、レプリケーションの並列化など 3 件を、考えただけで報告しなかった | 効果は不明のまま終わった |
| 報告を否定側へ強めて要約する | 調査を任せた subagent の「この案は今は効果が見込めない」を、「安全な変更はない」という広い結論として扱った | 別の有望な案（初期データの画像のファイル化）が、検討されないまま終わった |
| 検証の設計が反証に偏る | 候補を検証する subagent に「不確かなら反証された扱いにする」と指示した | 不確かな候補はすべて落ちる。試せば分かったかもしれない案も残らない |

## 2. 得を損と同じ精度で見積もる

損を数えたら、同じ形式で得も数える。損だけが具体的で、得が「たぶん速くなる」で終わっている見積もりは使わない。

- **どの資源が空くか:** DB の CPU、接続、IO、ネットワークの往復のどれが、どの時間帯に、どれだけ減るか。
- **非線形の効果:** 飽和した資源の負荷を減らすと、待ち行列が短くなり、残りの全要求が速くなる。待ち時間の単純な合計では過小評価になる。
- **得点の重み:** リージョンの倍率、配点、加点の上限。
- **採点の仕組み:** 期間内の成功率で利用者数が決まるような採点では、応答時間の短縮が利用者数を通じて何倍にも効く。
- **後続の改善:** その変更が、次にどんな改善を可能にするか（例: 読み取りを手元のレプリカへ移すと、共有 DB の負荷が下がり、別の改善の余地が生まれる）。

見積もりは幅で書く。損と得の幅が重なるなら、結論を出さずに入れて、公式走行で決める。

## 3. 見送ってよい理由は 2 つだけ

| 分類 | 扱い |
|---|---|
| 規則・仕様に違反する | 見送る。規則の該当箇所を書く |
| 公式走行で効果がない、または悪化した | 見送る。走行の記録を書く |
| 未検証、損がありそう、時間が足りなそう | 見送りの理由にしない。入れて走らせる |

「リスクが大きい」「時間がない」は、終了直前の最終得点を確定させる段階になるまで、見送りの理由にしない。
見つけた損は、却下の代わりに「採用後に減らす課題」として、減らす方法の候補と一緒に記録する。

## 4. 検証と要約を対称にする

- 候補を検証させるときは、失敗の仕方と得の大きさの両方を見積もらせる。「不確かなら反証された扱い」にしない。不確かなら「試す」に倒す。
- subagent の報告を引用するときは、結論と前提（調べた範囲、使ったデータの時点）をそのまま書く。「今は効果が見込めない」を「危険」「安全な案はない」に言い換えない。
- 考えた案は、採否にかかわらず全て人間に報告する。報告には、見込める得の幅と、試すのに必要な作業を添える。

## 5. 終盤の判断

- 最後の走行が最終得点になる大会で、走行間のばらつきが大きい場合、再走行は「今の得点を失う損」だけでなく「最高得点を更新する得」も持つ。両方を、測ったばらつきの分布から数字で示す。
- 再走行をやめるよう勧める前に、残りの投入回数と、各回で更新できる確率を示し、判断を人間に委ねる。
- 終了直前の段階でも、規則の確認と再起動後の動作の確認は続ける。それ以外の「念のため止める」は、根拠の数字がなければ勧めない。
- ログや profile を止める作業は、終了直前ではなく、最終得点を確定させる段階に入る時点で済ませ、その構成で公式走行を通す。

## 6. エージェントへの指示の例

作業の開始時に、次をエージェントへ渡す。

```text
候補を評価するときは、損と同じ形式で得を見積もる（空く資源、非線形の効果、得点の重み、採点の仕組み）。
見積もりは幅で書き、幅が重なるなら入れて公式走行で決める。
見送ってよいのは、規則違反と、公式走行で効果がなかった場合だけ。
未検証・損がありそう・時間が足りなそうは、終了30分前までは見送りの理由にしない。
見つけた損は却下の理由にせず、採用後に減らす課題として記録する。
考えた案は全て報告する。subagent の結論は前提ごと引用し、否定側へ強めて要約しない。
```
