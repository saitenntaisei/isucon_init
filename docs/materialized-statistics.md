# 繰り返す全件集計をトランザクション内の差分更新へ置き換える

統計APIが毎回同じ履歴を集計するなら、集計済みの行を保持し、元データの更新時に差分を反映する。
狙いは返却行数やアプリのソートだけでなく、読取のたびに繰り返す履歴走査をなくすことにある。
先に [計測と並行処理の手順](isucon-measurement-and-concurrency.md) で負荷区間と更新経路を確認する。

## 1. SQLへ計算を移すだけで走査が残らないか調べる

全員分の集計をGoへ返して順位を計算する処理は、SQLのCOUNTへ変えると転送行数が減る。
ただし、そのCOUNTの内側で毎回全履歴をGROUP BYしていれば、DB側の仕事は残る。
実験記録でも、この書換えだけでは増点を確認できず、集計表を差分更新する候補では改善が見られた。
後者も限られた回数の観測であり、特定の改善率を他の構成へ当てはめることはできない。

変更前に、対象SQLの呼出し回数、走査・返却行数、総経過時間、DBのCPUとlock待ちを保存する。
RAM上のDBでも、JOIN・GROUP BY・式評価・結果転送は残るため、I/O待ちだけで判断しない。

## 2. 集計の単位と更新表を先に決める

例えば「対象ごとの反応数・投稿数・金額合計」と「所有者ごとの合計」を持つ場合、
対象IDを主キーとする表と、所有者IDを主キーとする表を用意する。
値の帰属先は仕様から決める。投稿者と対象の所有者を取り違えない。

| 元データの変更 | 対象の集計行 | 所有者の集計行 |
| --- | --- | --- |
| 所有者作成 | まだ作らない | 全項目0で作成 |
| 対象作成 | 全項目0で作成 | 合計は変えない |
| 反応追加 | 件数+1 | 件数+1 |
| 金額を含む投稿追加 | 件数+1、金額加算 | 件数+1、金額加算 |
| 投稿削除・取消 | 削除した件数・金額を減算 | 同じ差分を減算 |

実際には編集、所有者変更、親の削除、一括投入、管理コマンドも洗い出す。
存在しない操作は実装の前提として記録し、新しい更新経路を追加する際の確認項目にする。
重複イベントや再試行を無条件に加算せず、元データで成立した変更と同じ回数だけ反映する。

初期値は親テーブルから作り、子が0件の対象や対象を持たない所有者も含める。
独立した複数の子テーブルは、それぞれ対象IDで集計してからLEFT JOINする。
反応3件と投稿4件を直接JOINすると12行になり、件数も金額も水増しされ得る。
NULLを0へ変換する場所、空集合、負数の可否、合計が収まる整数型も仕様に合わせる。

## 3. 正本と集計表を同じトランザクションで更新する

InnoDBなら元行のINSERT/DELETEと集計のUPDATEを同じトランザクションへ入れる。
アプリで両方を更新する方式と、DBトリガーで維持する方式を比較する。
トリガーは複数アプリからの書込みも捕捉できるが、TRUNCATEなど発火しない操作は別途扱う。
例外・rollback時に集計だけ残らず、commit済みの元行だけが数えられることを確認する。

増減は `SET count = count + ?` のようにDB内で行い、アプリで読んだ値による上書きを避ける。
全経路のlock順をそろえる。例えば対象の集計行を更新してから所有者の集計行を更新する。
複数対象を一度に更新する場合の順序も決め、deadlock時はトランザクション全体を扱う。
同じ所有者への大量投稿は1行を取り合うため、差分更新で新しい直列化点ができる。

MAX/MINやお気に入り項目は、COUNT/SUMと同じ加減算では維持できない。
最大値を持つ行の削除には再計算や順序付き索引が必要になる。
まずCOUNT/SUMだけを差分化し、MAXは対象IDで絞って読む構成も候補になる。
対象の値と順位などを複数SQLで読むなら、必要な同一スナップショットを分離レベルまで含めて確認する。

## 4. 順位の意味と比較順を保つ

得点が同じ場合にIDの降順で並べる仕様なら、`(score, item_id)` の複合索引を候補にする。
対象の得点とIDを取得し、対象より前に来る行だけを数える。

```sql
-- 同点もIDで区別する、1始まりの順位の例
SELECT COUNT(*) + 1
FROM item_statistics
WHERE score > ? OR (score = ? AND item_id > ?);
```

同点者が同じ順位になる仕様やdense rankには、この式をそのまま使わない。
順位の値、上位一覧の順序、ページ境界の第2キーまで元の仕様と照合する。
索引があっても前に来る行のCOUNTは行数に応じた仕事になる。定数時間になるとは扱わない。
実行計画で索引の使われ方と走査行数を確認する。

同点時に文字列を比較する場合、Goの文字列順とDBの照合順序が一致するとは限らない。
大文字小文字、アクセント、末尾空白などを確認する。
仕様がバイト辞書順ならVARBINARYなどで同じ比較を表現し、長さや索引制限も確認する。
ユーザー検索の照合規則と、順位の比較規則は分けて扱える。
scoreを生成列にする場合も、加算式・型・索引更新の費用を維持する必要がある。

## 5. 初期化と新しい更新経路を整合させる

初回の導入と競技の初期化では、元データと集計表の対応を一度に成立させる。
書込みを停止して構築するなら、次の順序を一つの手順として保存する。

1. 全writerを止め、進行中の更新が完了したことを確認する。
2. 専用トリガーを外して初期データを投入し、子ごとの集計から派生表を作り直す。
3. 0件の親も含む件数・合計を正本と照合し、トリガーを作成する。
4. 新しい読取実装を起動し、受付を再開する。

書込みを続けながら構築する方式では、構築中の更新を欠落・二重反映させない別の移行設計が必要になる。
通常のプロセス起動でこの初期化を実行せず、再起動後も正本と集計表を一緒に復元する。
旧版へ戻す場合もwriterを止め、集計更新を外してから旧読取を再開できるようにする。
新規INSERTだけでなく、削除、rollback、同時更新、再初期化後の新規作成を検証する。

プロセス内メモリの集計は別の選択肢になるが、DBトリガーと同じ共有性はない。
全更新を一つの所有者へ集めるか、順序・重複・欠落を扱う同期方式が必要になる。
プロセスを増やす前に [正本・更新・並行性・復元の契約](isucon-playbook.md#5-定石は観測結果に合わせて選ぶ) を見直す。

## 6. 減った読取と増えた書込を合わせて採否を決める

同じ負荷区間で、旧集計SQLの消失、順位SQLの件数・走査行数、APIの応答時間を確認する。
同時にINSERT/DELETEの時間、lock待ち、deadlock、DBのCPU、初期化時間を測る。
集計行と順位索引の更新で書込みは重くなるため、読取だけの改善で採用しない。
SQLの累積経過時間はCPU時間ではなく、トリガーの内外の時間を足すと重複し得る。
件数が違う計測同士では総時間だけを比較せず、要求数と成功数も残す。

実験では全件集計が減る一方でINSERTは遅くなり、最終的には全体得点で採用が判断された。
手元でも独立した候補として比較し、差が小さければ増点は未確定と記録する。
測定項目と復元の条件は [batch・索引の費用](isucon-measurement-and-concurrency.md#5-batch化と読み取り用索引は増える費用まで測る) と合わせる。
