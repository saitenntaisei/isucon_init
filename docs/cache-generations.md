# 変わらない参照データを初期化世代ごとに保持する

短い TTL のキャッシュは、値が変わらない間も SQL、転送、行の変換を繰り返す。
作成後に変わらない参照データなら、初期化まで保持し、関連データの組み立ても再利用できる。
DB がメモリに収まっていても、この処理と通信の削減には意味がある。

全体の進め方は [共通プレイブック](isucon-playbook.md)、
基本的な公開順序は [読み取りキャッシュの整合性](../README.md#読み取りキャッシュの整合性) を参照する。
ここでは、有限 TTL から世代単位の保持へ進むための条件を扱う。

## 1. 値が変わらない範囲を、書き込み経路から決める

画面上で編集できないだけでは不十分。通常更新、管理処理、削除、再試行、初期化まで追う。
関連テーブルやトリガーによる変更も含め、次のように分類する。

| データ | 保持の単位 | 更新時の扱い |
| --- | --- | --- |
| 作成後は変更・削除しない本体と関連行 | 初期化世代 | commit 後に追加 |
| 初期化時だけ変わるマスタ | 初期化世代の全件 snapshot | 世代ごと交換 |
| 画像、状態、権限、集計値 | 本体から分離 | 個別の鮮度契約に従う |
| 存在しない ID | 原則保持しない | 他プロセスの追加を DB で発見 |

「本体は不変」でも、参照先の名前や画像が可変なら応答全体は不変ではない。
権限や利用者ごとの状態を共通テンプレートへ混ぜない。
削除や ID 再利用が通常操作にある場合、この方式をそのまま適用しない。

## 2. 完成した snapshot を公開する

起動時は、正本から本体・関連行・マスタを一つの整合した読み取り snapshot で取得する。
別々に読んだ時点が混ざると、本体だけ存在して関連行が欠けたキャッシュを作りうる。
非公開の store に組み立て、読取 transaction の終了も確認してからポインタを交換する。
起動のために DB を初期化してはいけない。

preload に失敗した場合は、起動を失敗させるか、明示的に DB 直読へ切り替える。
途中まで作れた store を「全件取得済み」として公開しない。
読み込み時間は初期化の制限時間に含め、メモリの一時的な二重保持も見積もる。

初期化では、通常リクエストを止め、進行中の書き込みを排出してから DB を入れ替える。
各プロセスが新世代の store を準備したことを確認して、通常トラフィックを再開する。
ポインタ交換だけでは、初期化前の transaction が初期化後の DB へ書く競合は防げない。

## 3. リクエストを開始時の store に結び付ける

初期化が世代番号と store を交換しても、進行中のリクエストは開始時の store を使う。
完了時に「現在の store」を取り直すと、古い DB 観測が新世代へ紛れ込む。

```text
request 開始:
    scope = atomic_load(current_store)  // 世代と map を一緒に取得
read(key):
    if scope に正の値がある: return value
    value = 正本を読む
    見つかった正の値だけを scope の公開候補へ追加
write:
    DB transaction を commit
    commit 成功を確認できた値だけを公開候補へ追加
publish:
    lock(scope)
    scope に公開候補を追加         // current_store へは追加しない
initialize:
    書き込み停止・排出・DB 初期化・新 store 構築
    atomic_swap(current_store, new_store)
```

store 内の追記と参照には別途排他が必要。ポインタの atomic 操作は map を保護しない。
commit 失敗・結果不明の書き込み値は公開しない。HTTP 成功だけを commit の代わりにしない。
別プロセスの新規作成は miss 時に正本から取り込み、既存の正の値は失効させない。
古い store は、それを使うリクエストがなくなってから解放する。

## 4. 応答の固定部分も再利用する

本体、順序を保ったタグ列、固定フィールドをテンプレートとして保持する。
要求ごとにコピーへ可変の画像情報や利用者固有の状態を埋め、認可は毎回行う。
共有テンプレート自体を書き換えず、slice・map の参照共有にも注意する。
関連行の重複、並び順、NULL、空配列と null の違いを元の応答に合わせる。

テンプレートの再利用と SQL 行の保持は独立した候補として測る。
再利用のために可変項目まで固定すると、hit 率が高くても古い応答を返してしまう。

## 5. メモリ上限と効果を確認する

件数だけでなく、文字列、関連行、map、テンプレート、リクエスト中のコピーも測る。
容量超過時は、新しい値の保持を断って正本へフォールバックできるようにする。
保持しなかった値を「不存在」と扱わない。巨大な関連行を持つ単一キーにも上限を設ける。

| 確認項目 | 比較する値 |
| --- | --- |
| 再利用 | 種類別 hit/miss、容量拒否、元の SQL 回数、組み立て回数 |
| 初期化 | preload 時間、完了した世代、初期化を繰り返した後の正しさ |
| メモリ | 使用量、ピーク、GC、排他待ち、旧 store の滞留 |
| 利用者への効果 | API の遅延分布、成功数、タイムアウト、公式得点と PASS |

再現環境では、不変な参照データの保持を単独で導入した候補で SQL が減り、得点も改善した。
一方、一覧を読むたびに DB から版番号を取得する別候補では、一覧の hit が一度もなく、
従来の一覧 SQL に版確認の往復が加わった。固定部分の高い hit 率だけでは採用できない。
miss の理由は、更新、未登録、容量拒否、キーの違いに分けて記録する。

これらは個別環境の観測であり、キャッシュ一般の効果を保証しない。
計測ログの有無や空き容量も揃え、複数の変更を混ぜずに比較する。
SQL 累積 elapsed は CPU 時間と区別する。単発の得点差から原因を断定しない。
鮮度が必要な可変データには、[更新直後の読取](isucon-field-notes.md#4-キャッシュ再構築の殺到と更新直後の読取を分ける)
と全更新経路の整合性設計が別途必要になる。
