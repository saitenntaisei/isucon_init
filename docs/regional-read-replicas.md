# 地域ごとの読み取りレプリカと構造変更の評価

[共通手順書](isucon-playbook.md) と [参加記から学ぶ実践ノウハウ](isucon-field-notes.md) を補う。
ISUCON2026本選では、アプリが複数リージョンにあり、DB は 1 台を共有していた。
遠いリージョンのアプリに読み取り専用の同期レプリカを置き、得点を 1 回の走行で 26% 上げた。
この構成を提案されたとき、AIエージェント（Claude Code）は書き込みが遅くなる損だけを強調し、効果を見積もれなかった。
その反省を含めて、構成と評価の仕方を一般化する。数値は判断の根拠として示す例である。

## 1. 構造変更をコストだけで評価しない

提案時、エージェントは次のように見積もった。

- 損: 全ての書き込み（1 走行で約 8,150 件）が、遠いレプリカでの反映（RTT 約 100 ms 以上）を待つ。DB の近くにあるリージョンの書き込みも遅くなる。
- 得: 遠いリージョンの読み取り（約 7,900 件）が、それぞれ約 100 ms 速くなる。
- 結論: 待ち時間の合計ではほぼ相殺し、どちらに転ぶかはわからない。

実際は 1 回の走行で 46,247 点から 58,388 点（+26%）に上がり、この構成が最終構成の土台になった。
見積もりが外れたのは、次の 3 点を落としたためである。

1. 共有 DB は CPU が飽和していた。全読み取りの約 36% が DB から外れると、残りの要求の待ち行列も短くなる。飽和した資源の負荷を減らす効果は、待ち時間の単純な合計より大きい。
2. 遠いリージョンには得点倍率（1.5 倍）があった。
3. 採点が期間内の成功率で利用者数を決める仕組みだと、応答時間の短縮は利用者数を通じて何倍にも効く。

エージェントが見つけた損（書き込みの遅延）は実在し、後で接続 pool の待ちとして現れた。
しかし、それは構成を却下する理由ではなく、次の改善の課題だった（4 章）。

決まり:

- 人間が提案した構造変更を、目に見える局所的なコストだけで評価しない。共有資源の負荷の変化、得点倍率、採点の仕組みを含めて見積もる。
- 見積もりが拮抗するなら、反対せずに入れて公式走行で決める。
- 見つけたコストは却下の理由にせず、採用後の改善課題として記録する。

この傾向は構造変更に限らない。一般化した手順は [AIエージェントの損の過大評価を正す](agent-cost-estimation.md) にまとめた。

## 2. 構成

- 遠いリージョンのアプリサーバーに PostgreSQL を置き、共有 DB から論理レプリケーションでメタデータだけを複製する。大きな binary（画像 bytes）は複製しない。
- 遠いリージョンの読み取りは手元のレプリカで行い、書き込みは共有 DB へ送る。
- 書き込みの成功後の読み取りは、他リージョンでも結果を反映する必要がある。共有 DB を `synchronous_standby_names = 'FIRST 2 (s2, s3)'` と `synchronous_commit = remote_apply` にして、両レプリカが反映するまで commit を返さない。
- 論理レプリケーションの apply は commit 順なので、commit が返った時点で、それより前の書き込みも両レプリカに反映されている。
- レプリカで読まない表（primary だけで読む通知など）は、複製対象から外すと decode と apply の量が減る。

## 3. 一貫性の落とし穴

反映前の読み取りで不正判定になる事例は [参加記から学ぶ実践ノウハウ](isucon-field-notes.md) にもある。
本選では、損を減らそうとした部分的な非同期化が、一貫性を壊す設計だった。

- 案: 「DB の近くのリージョンのセッションは、そのリージョンでしか認証しない」と考え、ログイン・ログアウトだけを非同期の commit にする。
- 反例: 遠いリージョンのアプリは、リージョンの検査より前にレプリカでトークンを照会する。レプリカに行がまだ届いていないと、本来の 403（リージョン不一致）ではなく 401 を返す。ベンチの整合性検査で FAIL になり得る。
- 成立させるには、「利用者とサーバーのリージョンが一致するときだけ非同期にする」と「レプリカで見つからないときは primary で再確認する」の両方が要る。

非同期化を入れる前に、次を確かめる。

- [ ] その書き込みを読む可能性がある全ての経路（認証、権限、リージョン検査を含む）と、各経路が読む DB。
- [ ] 経路の途中でレプリカを読む箇所があるか。あれば、行がない場合と古い場合の応答。
- [ ] 書き込んだ要求の中で、commit 後にレプリカから読むハンドラがないか。

## 4. 書き込みの損を後から減らす

同期レプリケーションでは、書き込みが反映待ち（本選では p50 70 ms）の間も DB 接続を握る。
書き込みの多いリージョンでは、これが接続 pool の待ちになった（1 走行で 32,163 回、合計 11,491 秒）。

1. 接続 pool の待ちを `DBStats` で測る。
2. DB の `max_connections` と pool の大きさを、backend 1 本あたりのメモリと MemAvailable から決めて広げる。
3. 書き込みを非同期の commit で返して接続を pool に戻し、HTTP 応答の前に専用の接続で `remote_apply` の commit を 1 回だけ待つ。複数の要求でこの 1 回を共有する。これで反映待ちが接続を握る時間から外れる。本選ではこの変更を入れた走行で 13% 上がった（走行間のばらつきを含む）。

## 5. 運用

- `FIRST 2` で両レプリカを待つ構成では、片方のレプリカが止まると全ての書き込みが止まる。競技時間内に全ホストを同時に再起動し、レプリカの自動起動、追いつき、アプリの起動時の再試行を確かめる。
- レプリカ側の表に制約を足す・緩める migration は、subscriber 側を先に変える。逆順だと apply worker がエラーで止まり、全ての commit が待ち続ける。
- アプリの起動時に、レプリカの購読状態（全表が ready か）と、共有 DB の同期設定を検査する。不一致なら起動しない。
