# 複数プロセスの可変キャッシュへ更新を公開する

可変データの短い TTL をなくすには、全ての書き込み経路から更新を届ける必要がある。
ここでは DB を正本とし、commit 済みの値を全配信プロセスへ同期公開する方式を扱う。
対象は小さい値で、更新数と配信プロセス数が少なく、公開の往復を許容できる場合である。

全体の判断は [共通プレイブック](isucon-playbook.md)、
プロセス内の競合は [読み取りキャッシュの整合性](../README.md#読み取りキャッシュの整合性) を参照する。
全経路の管理が難しい場合は、仕様を満たす TTL、DB 直読、書き込み元の集約も比較する。

## 1. 成功応答が保証する範囲を決める

例えば「更新の成功応答後に始めた読取は、その版かそれ以降を返す」を契約にする。
更新中の読取や、更新前に始まった読取まで同じ保証に含めるなら、別途直列化が必要になる。
同期 push は、DB commit と全キャッシュへの反映を一つの原子的操作にする仕組みではない。

通知先は設定ファイルに並ぶ台数ではなく、実際に対象データを配信している全プロセスである。
同じホストの複数 worker、自分自身、別経路の origin も含めて確認する。
参加・再起動したプロセスは、正本の読み込みと更新追随が済むまで振り分け対象にしない。
snapshot の構築中に更新する場合は差分を追いつかせるか、その間の書き込みを止める。

## 2. 初期化世代とデータの版を分ける

公開メッセージは少なくとも `(世代, キー, 版, 値または削除)` を持つ。
版はキーごとの更新順を表し、値と同じ DB transaction で確定させる。
例えば対象行をロックして版を加算する。時刻や任意の採番 ID が commit 順を表すとは限らない。
自動採番を流用するなら、同じキーへの並行更新でも順序が一致することを確認する。

SQL による miss 補充も push も、同じ版比較を通す。
古い SQL が後着しても、受信済みの新しい値を上書きさせない。
削除は版付きの墓標として扱い、古い補充による復活を防ぐ。
同じ版・同じ値の再送は冪等にし、同じ版・異なる値は異常として扱う。

```text
受信または SQL 補充:
    lock(cache)
    if message.generation != current.generation: reject
    if message.version < known_version[key]: 古い値を捨てる
    if message.version == known_version[key]: 同じ内容なら再送として受理
    if message.version > known_version[key]: 値と版を一緒に更新
    unlock(cache)
```

この処理は、保持した版の下限が失われないことを前提とする。
単にエントリを evict すると、以前の SQL 補充が旧版を入れ直すことがある。
版の下限や補充開始時の世代を保持するか、無効化後の旧補充を拒否する仕組みを併用する。

初期化時は更新を止め、進行中の書き込みを排出し、全ノードで世代を切り替える。
旧世代の push を受け入れてはいけない。DB の ID が初期化で再利用されても区別できるようにする。
リクエスト内に一度取得した値を保持するキャッシュや、応答テンプレートも確認する。
新しい読取が古いリクエストの結果を共有しないよう、版と共有範囲を揃える。

## 3. commit 後に全配信ノードの ACK を待つ

1. DB 更新を commit し、確定した版と値を取得する。
2. 認証された内部経路で、全配信ノードへ同じ更新を送る。
3. 受信側は値と版の反映、または後述の DB 直読への切替を終えて ACK する。
4. 全ノードの受理を確認してから、更新 API の成功を返す。

ACK は「HTTP を受け取った」ではなく、そのノードが契約を守って読取を処理できる意味にする。
より新しい版を既に持つ場合も、世代と内容の整合性を確認したうえで ACK できる。
一つの送信に失敗しても、他のノードへの送信を省略しない。

DB commit 後の公開処理をクライアントの切断だけで中断しない。
上限時間のある別 context で継続し、同じ版を冪等に再送する。
再試行には回数・時間の上限を置き、更新 API の制限時間と公開遅延を測る。
有限回の retry は障害回復の保証ではないため、失敗時の配信方針も実装する。

## 4. 容量不足と途中失敗を成功扱いしない

容量上限に達していても、既存キーの更新を拒むと、そのキーが古いまま残る。
既存キーは置換し、新規キーを保持できない場合は、結果を明示して DB 直読へ切り替える。
その切替で進行中の旧補充も無効にし、古い値や派生テンプレートを返さないようにする。
安全に DB 直読へ切り替えられない場合は、受信を失敗させる。

| 状況 | 必要な扱い |
| --- | --- |
| DB commit 失敗 | 未確定値を公開しない |
| commit の結果不明 | 正本と操作 ID で確認し、未反映と決めつけない |
| 一部ノードだけ受理 | 未受理ノードを直読へ切り替えるか、振り分けから外す |
| ノードと通信不能 | 遠隔無効化できたと仮定せず、配信を止める仕組みを使う |
| 容量拒否 | 古い値の保持を続けたまま ACK しない |
| 更新元プロセスが停止 | 再同期するまで古い状態を配信させない |

更新 API を 500 にするだけでは、古いキャッシュを配信し続ける問題は解決しない。
また、500 やタイムアウトでも DB には変更が残っている場合がある。
呼出側が安全にやり直せるよう、操作 ID、冪等な更新、確定結果の照会などを設計する。
commit 直後のプロセス停止まで扱うなら、DB に公開予定も残す方式や、復旧時の全件再同期が必要になる。
送信元のメモリだけにある retry では、失われた公開処理を復元できない。
この方式は write-behind ではなく、成功前の DB commit を省略する理由にはならない。

## 5. 成功例と失敗順序を両方測る

再現環境では、画像の版とハッシュを同期公開して周期的な再取得 SQL をなくし、得点も改善した。
その後、容量上限で既存値が更新されない問題と、切断時に公開を中断する問題を修正した。
正常系のベンチ PASS だけでは、これらの失敗条件を確認できない。
世代付き公開や通信不能ノードの除外も、環境に応じて別途実装・検証する必要がある。

最初に更新の成功直後、全 origin を個別に読んで同じ版が得られることを確かめる。
次に旧 SQL 補充の後着、並行更新、重複送信、削除、容量上限、切断、ACK 喪失、初期化を試す。
同じプロセスで初期化を繰り返す試験と、再起動時に正本から戻す試験は分けて行う。

計測では hit/miss、拒否した旧版、送信失敗、再送、公開時間、DB 直読への切替数を残す。
減った読取 SQL と増えた更新経路の待ちを、API 遅延・成功数・得点で比較する。
単発の得点差を保証にせず、[途中失敗と再試行の契約](isucon-measurement-and-concurrency.md#4-外部副作用をtransactionの外へ出す前に契約を決める)
も含めて採否を決める。
