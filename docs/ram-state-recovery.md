# RAM上のDB状態を正常再起動で復元する条件

[共通手順書](isucon-playbook.md) の再起動確認を、RAM配置のDBと停止時snapshotについて補う。
これは適用条件の厳しい選択肢であり、標準のDB永続化を一律に置き換える推奨設定ではない。
利用可能な資源、禁止される変更、要求されるデータ保持と障害条件を先にマニュアルで確認する。
正常停止後の復元ができても、電源断や強制終了に耐えることにはならない。

## 1. どの仕事をメモリ化するかを分ける

| 方法 | 主に減らす仕事 | 残る仕事・性質 |
| --- | --- | --- |
| DBのbuffer poolを増やす | データpageの読み込み | SQL、lock、通信、結果変換、redoやdirty pageの書込 |
| datadirをtmpfsへ置く | DBファイルの通常のblock I/O | SQL、lock、通信、メモリコピー。永続化経路を別に設計する必要 |
| アプリで応答材料をcacheする | DB往復、SQL、繰り返す組立処理 | 無効化、更新反映、複数process間の整合性 |

buffer poolのdumpは再開時に温めるpageの情報であり、DB内容のバックアップではない。
datadirがRAMにあっても、CPUや接続待ちが律速なら応答は速くならない。
最初に同じ区間の要求時間、DB待ち、CPU、I/Oを測り、狙う費用が残っているかを確かめる。
詳細は [計測と並行処理](isucon-measurement-and-concurrency.md) を参照する。

## 2. 容量を全体で予算化する

表のデータ量だけでは必要なメモリを見積もれない。少なくとも次を含める。

- データと索引、redo・undo・binlogなど、datadirや関連pathに置くファイル。
- buffer pool、接続ごとのbuffer、sort・一時表などのDB内部メモリ。
- アプリのheap、cache、処理待ちqueue、proxyのbuffer、監視process。
- ログ、一時ファイル、初期化やsnapshot検証の作業領域、OS用の余裕。
- 負荷で増える行・索引・ログと、shutdown保存中にも必要なメモリ。

tmpfsのファイルpageとbuffer poolが同じデータの別のcopyを持つ分も数える。
tmpfsのsize上限は予約済みRAMではない。RSSの合計も共有pageを重複計上し得る。
実際のmemory使用量、MemAvailable、swap、OOM、tmpfs空き、初期化と走行中のpeakを合わせて見る。
tmpfsはswapされ得るため、RAM配置とディスク書込ゼロは同義ではない。
空きを作るために無条件でswapや保護機構を止める手順にはしない。

永続側にも、公開済みsnapshot、作成中snapshot、復旧用世代を同時に置ける容量が必要になる。
snapshot全体のcopyと検証にかかる時間が、実際のサービス停止猶予へ収まることも確認する。
走行開始時に収まっても、終了後のデータ増加で保存不能になる構成は採用しない。

## 3. 完了したsnapshotだけを公開する

以下は、DBの正常停止後にdatadir全体を保存する方式の必要条件である。
稼働中DBのファイルを単純copyして整合したbackupと見なさない。
オンラインで保存したい場合は、そのDBが対応する一貫したbackup手順を別途使う。

1. 全てのwriterを止め、受付済み更新と非同期queueを排出する。別ホストのwriterも対象にする。
2. DBを正常停止し、実際のprocess終了と停止結果を確認する。timeoutやSIGKILLを正常終了に含めない。
3. 今回のboot・DB起動世代に対応する正常停止記録を確認する。古い成功記録を流用しない。
4. 新しい世代のstaging領域へ、必要なDBファイルと復元metadataをcopyする。
5. ファイル集合・内容・所有権などを検証し、必要なfileとdirectoryを永続側へ同期する。
6. 同一filesystem上で完成世代を確定し、参照先をatomicに切り替え、親directoryも同期する。
7. 新しい世代の公開が完了するまで、前の完成世代を削除しない。

途中失敗で「最新」の参照が不完全な世代を指さないようにする。
renameのatomic性だけでは、電源断後も参照が残る保証にはならない。
公開metadataにはschema・DB版・世代・対象ファイルと検証結果を含め、復元側も確かめる。
前の完成世代を残すことと、最新の受付済み更新を保存できたことは別の条件である。

停止処理の失敗を返しても、OSのshutdownが継続する場合がある。
「停止hookがあるから保存済み」と扱わず、保存完了と起動時に選んだ世代を記録する。
保存失敗時は最新データの保持を確認できるまで復旧済みとしない。
停止時だけ保存する設計では、強制終了時に最後の完成snapshot以降の更新を失い得る。

## 4. mount・復元・DB・アプリの順を固定する

起動時は `永続領域とRAM領域のmount → 完成世代の復元 → DB → 利用サービス` とする。
停止時は利用サービスの更新を排出してからDBを止め、保存完了後にRAM領域をunmountする。
systemdの`After=`は順序を指定するだけなので、起動する依存関係も別に確認する。
停止時には順序が反転するが、別ホストの停止順までは保証しない。
復元は既存データを読み戻す処理であり、初期データを作り直す処理にしない。

補助pathの移設・撤去時は、サービス一覧だけでなく次も調べる。

- socket activationやtimerから再起動されるwriter。
- 初期化scriptの`mktemp`先、proxyの一時path、DBのerror logや一時領域。
- unmount対象の中に置いた管理script自身のlockや開いたfile descriptor。
- 削除したpathや旧inodeを保持したままのprocess。

サービスがactiveでも、初期化用の作業pathが消えて初期化だけ失敗した例がある。
移設と撤去の両方向を検証し、後述のデータ保持確認を終えた後で初期化経路も確認する。

## 5. 設定変更を復元方式と一緒に管理する

DBのinclude先やoverlayを変更すると、保存済みデータを扱う前提が変わる場合がある。
構成管理外のoverlayを検知した起動前検査がDB起動を拒否し、overlay撤去で復旧した例がある。
検査を削除して起動させるのではなく、変更を戻すか、対応する移行手順で管理対象へ取り込む。

DB版、実効設定、datadirと関連path、mount、補助script、unit/drop-inを構成として記録する。
意図した変更は停止・保存・復元の双方へ反映し、適用途中の失敗からの復旧先を用意する。
RAMに置いたことを理由に、redo・doublewriteなど別の保証まで無検証に弱めない。

## 6. 初期化する前にデータ内容を照合する

正常再起動の検証では、初期化が既存データを消して不具合を隠すのを避ける。

1. 更新を完了させて全writerを静止し、対象table集合、schema、内容の照合情報を保存する。
2. 規定の対象ホストを正常再起動し、boot IDの変化、自動起動、復元世代、停止ログを確認する。
3. 初期化・ベンチ・新しい書込の前に再び静止し、同じ対象と方法で内容を照合する。
4. binary値や更新済み行を含め、APIから取得できる内容とDBの内容を必要な範囲で確認する。
5. データ保持の確認後に初期化と公式ベンチを実行し、結果と未検証範囲を残す。

件数や最大IDの一致は、欠落の一部を見つける手掛かりであり、全行の内容一致を証明しない。
checksumやdigestは対象列、NULL・binaryの扱い、順序、対応するDB版をそろえ、未対応値を成功扱いしない。
アプリ状態を複数DBやfileへ分けた場合は、その対応関係も確認する。
サービス起動、SQL疎通、初期化成功、公式PASS、再起動後の内容一致は別々に記録する。
この試験の成功から、未実施の電源断・強制終了や仕様全体への適合を主張しない。
