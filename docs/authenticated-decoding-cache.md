# 認証済みペイロードのデコードを再利用する

署名付きセッションを毎リクエスト復号・デコードする構成では、同じバイト列を同じ値へ
変換する処理がCPUやallocationの上位に出ることがある。認証の検証を毎回実行したうえで、
その内側の決定的なデコードだけを再利用する候補を検討する。
候補選定と採否は[計測と並行処理の手引き](isucon-measurement-and-concurrency.md)に従う。

## 使える境界をライブラリの呼び出し順で確認する

次の順序を、使用中のライブラリのバージョンと実際の呼び出し元で確かめる。

```text
要求ごと: 長さ・形式 → 署名/MAC・期限 → 必要なら復号
                                      ↓
再利用可: 検証を通った同一ペイロード → 同一の不変な値
                                      ↓
要求ごと: アプリの期限・失効・利用者の状態・操作の認可
```

署名検証を含む上位の「セッション取得」全体をキャッシュすると、失効や期限の確認を
飛ばす可能性がある。キャッシュを置くのは検証の後にあるserializerの境界とし、
キャッシュhitでも上流と下流の検証を通ることを確認する。
単なるデコード結果には、現在の権限やDBのユーザー有効性を付け加えない。

gorilla/securecookieを使った事例では、MAC・時刻検証と任意の復号の後に呼ばれる
`Serializer.Deserialize`を包み、`Serialize`は元の実装へ委譲した。
読み書きするcookieの形式を維持できるため、旧版と候補版の混在やrollbackに伴う
強制ログアウトを避けられる。ただし、この実行順は別のライブラリへそのまま当てはめない。

## キャッシュが返すのは値だけにする

| 項目 | 設計条件 |
| --- | --- |
| キー | 検証後にデコーダへ渡る正確なバイト列と、デコード規則の識別子 |
| 値 | 型を確認した不変なprimitive値など、共有による変更が起きない表現 |
| hit時 | リクエスト専用のmapや構造体を作る。可変な子要素も共有しない |
| miss時 | 元のデコーダを実行し、成功した対応範囲の値だけを保存する |
| 未対応入力 | 元のデコーダへ委譲し、エラー、型、未知フィールドの扱いを変えない |

ユーザーIDやセッションIDだけをキーにすると、期限や追加フィールドが異なる入力を
同一視してしまう。短縮hashだけで一致とせず、hashを使う場合も元の入力との一致を確かめる。
キーのバイト列は保持時にコピーし、呼び出し元が再利用するbufferを参照し続けない。

デコーダが既存mapへmergeするAPIなら、空のmapだけをキャッシュ対象にするなど、
元の動作を維持できる範囲を限定する。任意の出力型を無理に共通化しない。
ライブラリのエラーや途中までのデコード結果を成功結果として保存しない。

## 容量と寿命を決める

件数だけでなく、入力の最大サイズ、値のサイズ、キーやmapの管理費を含むメモリ上限を決める。
対象外の大きな入力でも、元のデコーダが許す入力なら通常経路で処理する。
TTLを付ける場合はhitで延長するかを明記し、期限切れentryが残る場合も容量上限を守る。
全miss時の同期、並行miss、evictionの費用を含めて比較する。

キャッシュのTTLは認証の有効期限ではない。期限切れcookieはキャッシュに値が残っていても
毎回の期限検証で拒否する。鍵を廃止した後も、その鍵の検証に成功したという結果は再利用しない。
codecやschemaの変更時には別のcacheを使うか世代を切り替え、異なる規則の値を混ぜない。

同一バイト列から同一の値への変換だけなら、通常はノード間のcache同期は不要になる。
一方、デコード中にDBや失効リストを参照する実装ではこの前提が成立しない。
利用者状態や権限を含むcacheへ拡張する場合は、別途更新の整合性を設計する。

## 比較で確かめること

- 同じcookieを旧版・候補版で読み、値とエラーを比較する。候補版が発行したcookieも旧版で読める。
- 改ざん、期限切れ、廃止した鍵、異なるcookie名が、cache hit相当の状態でも拒否される。
- hit後のmapを変更しても後続要求へ漏れない。失効・認可の判定は毎回実行される。
- 未知フィールド、型違い、空でない出力先、大きな入力は元の挙動を保つ。
- 容量超過と並行missでメモリが有界で、同一入力の結果が変わらない。
- 公式ベンチの得点・失敗に加え、デコードCPU、allocation、hit率、応答時間を比較する。

認証後のGobデコードを再利用した比較では、形式を変えずに得点改善が反復して観測された。
これは当該負荷での候補の根拠であり、すべてのセッション処理の高速化を保証するものではない。
cache lookup、lock、新しいmapの確保が増えるため、デコードが軽い場合や入力の再利用が少ない
場合は採用しない。cookieやペイロード、キャッシュキーを診断ログへ出す必要はない。
