# AIエージェント運用と終盤判断の知見

[共通手順書](isucon-playbook.md) と [計測と並行処理](isucon-measurement-and-concurrency.md) を補う。
ISUCON2026本選で、実装をAIエージェント（Codex、Claude Code）に任せて得た実測と失敗を一般化した。
数値は判断の根拠として示す例であり、他の回の設定値としてそのまま使わない。
効果を公式走行で確かめた事項と、試していない事項を分けて書く。

## 1. 「危ない」で見送らず、戻す時間を見積もって試す

AIエージェントは、未検証の変更を「リスクが大きい」として自分で見送りやすい。
ISUCON2026本選の終盤、エージェントが見送った、または止めるよう勧めた判断のうち4件を人間が覆した。
覆した後の公式走行はすべてPASSし、2件で最高得点を更新した。最終得点もそのうちの1件で出た。

- 未検証の優先度制御を「試して戻す時間がない」として見送った。実施後の得点は直前と同等（-1.8%、ばらつきの範囲）だった。
- 書き込みの待ちを接続から外す変更を、全リージョンへ広げるのは時間が残っていればに限るとした。実施後に最高得点を更新した。
- 「最終走行が最終得点になる」規則を理由に、再走行と再起動後の走行を止めるよう勧めた。続けた再走行で最高得点を更新した。
- 自分で決めた最終投入時刻（終了25分前）の後にも走らせ、すべてPASSした。

他に、エージェントが考えただけで報告しなかった案が3件あり、効果を確かめないまま見送った案も複数あった。
これらは試していないので、効果は不明である。

運用の決まり:

1. 見送りの理由は「危ない」ではなく、戻す手順と所要時間で書く。例: 「env を1行消して再起動、1分」「前の commit を全ホストで build して再起動、3分」。
2. 戻す時間 + 公式走行1回分 + 復旧後の再走行1回分が残り時間に収まるなら、試す。
3. 考えた案は、採否にかかわらずすべて人間に報告する。見送った案には、試すのに必要な時間を添える。
4. 最終投入時刻は勘で決めない。公式走行の実測所要時間（待ち行列を含む）から逆算する。
5. 「規則上の禁止」「計測で効果なし」「未検証」を区別して記録する。未検証を危険と同一視しない。

## 2. 戻す時間を短くしておく

コードと設定は git で管理しているので、どの変更も前の版に戻せる。
試すかどうかを分けるのは戻せるかではなく、戻して公式走行に間に合うまでの時間である。

- 全ホストでの build、binary の置き換え、再起動まで含めた「前の commit に戻す」所要時間を一度測っておく。
- 新しい挙動を env で有効化すると、戻す操作は env の削除と再起動だけになり、build が要らない。
- 戻すときに使う binary を、各ホストに置いたままにしておく。

git の外にあるものは、git で版を戻しても戻らない。

- DB のデータ状態（migration で足した行や変えた制約）は、前の commit のコードを置いても戻らない。新版の起動時の検査が migration 前後の両方の状態を受け入れる形にしておくと、コードだけを戻しても起動できる。旧版の検査が新しい状態を拒否する場合は、DB を戻す手順も用意する。
- 論理レプリケーションでは、subscriber 側の制約を先に緩めてから publisher 側でデータを変える。逆順だと apply worker がエラーで止まり、同期レプリケーションなら全ての commit が待ち続ける。
- migration は、本番 DB で rollback する transaction の中で一度流してから適用する。SQL 関数の列名の誤りで、1 回の公式走行を失った例があった。
- サーバー上だけで変えた設定は、変えた時点でリポジトリの控えにも反映する。

## 3. 採点の構造を利用者数の推移から読む

ベンチの出力に、日ごと・リージョンごとの利用者数が出ることがある。
ISUCON2026本選では、4 日目までは利用者が毎日約 2.8 倍に増え、5 日目で止まる走行が多かった。
規則はマニュアルに書かれていなかったが、前日に期間内で投稿できた割合と翌日の伸びが対応していた（観測からの仮説）。

| 前日に期間内に投稿できた割合 | 翌日の人数の伸び |
|---:|---:|
| 100% | 1.73 倍 |
| 89% | 1.34 倍 |
| 56% | 1.0 倍 |

利用者数が成功率で決まる採点では、応答時間の短縮が利用者数を通じて何倍にも効く。
得点が伸び悩んだら、どの日・どのリージョンで伸びが止まるかを先に調べる。

## 4. 遅らせてよい要求は、利用者ごとの経路を復元してから決める

アクセスログの集計だけで「得点への寄与が小さい要求は遅らせてよい」と判断すると、外れる。
DB の各表の作成時刻から、利用者ごとに期間の開始から投稿までの書き込みを数えると、次の経路が見えた。

- その日に登録した利用者は「登録 → login → 友達申請 約 2 件 → follow → プロフィール画像 → 投稿」と直列に進む。ある走行の 4 日目では、新規の利用者は投稿まで平均 10.2 秒、既存の利用者は 2.9 秒だった。
- 投稿の前に届いた申請の一覧を取得して承認する利用者もいた。

1 件あたり 1〜3 点の要求でも、投稿の経路上にあれば遅らせると期間内に間に合わなくなる。一覧を遅らせると、ベンチ側でタイムアウトした。
履歴の閲覧などの重い読み取りを遅らせた走行では、同じホストの他の要求の応答時間がほぼ半分になり、新規の利用者が増えた。ただしこの走行では一覧も遅らせており、タイムアウトが出た。

手順:

1. 利用者ごとに、期間の開始時刻と各書き込みの時刻を DB から集め、投稿までの順序を復元する。
2. 新規の利用者と既存の利用者を分けて、投稿までの時間を比べる。
3. 経路上にない要求だけを、同時実行数の上限で遅らせる。上限は env で変えられるようにする。
4. ベンチの結果メッセージで、遅らせた要求のタイムアウトが出ていないかを確認する。

## 5. 接続を握る時間を測り、待ちを接続から外す

DB 接続 pool の待ちは、`database/sql` の `DBStats`（`WaitCount`、`WaitDuration`）を expvar で出せば測れる。
同期レプリケーションの反映待ちの間も書き込みが接続を握ると、待ち時間の大部分が接続の空き待ちになる。
ISUCON2026本選では、反映待ちは p50 70 ms だったが、書き込みの p50 は 0.6〜0.9 秒で、1 回あたり 0.4〜0.65 秒を pool の待ちに使っていた。

接続数を増やす前に、接続を握る時間を減らす。

- 書き込みは非同期の commit（`synchronous_commit = local`）で返し、接続を pool へ戻す。
- HTTP 応答の前に、専用の接続で同期の commit（`remote_apply`）を 1 回だけ行い、それを待つ。複数の要求でこの 1 回を共有する。
- 論理レプリケーションの apply は commit 順なので、この commit が反映されれば、それより前の書き込みも反映済みになる。
- 書き込んだ直後に、同じ要求の中で replica から読むハンドラがないことを確認してから入れる。

同じホストでこの方式を入れた走行は、直前の走行より 13% 高かった（走行間のばらつきを含む）。

接続数を増やすときは、DB の backend 1 本あたりの private memory と、走行後の MemAvailable から上限を決める。
PostgreSQL の `postgres -C shared_memory_size_in_huge_pages` は稼働中の data directory では lock file で失敗する。
`PG_VERSION`、`postgresql.auto.conf`、`global/pg_control` だけを複製した一時 directory で計算できる。

## 6. 走行のばらつきと最終得点の規則に合わせて走らせる

同じ構成で 5 回走らせると、得点は ±5% を超えて散らばった。1 回の差で採否を決めない。

- 候補の評価は、同じ構成の再走行を含めて比べる。
- 最後の走行が最終得点になる大会では、終盤に同じ構成を繰り返し走らせる。平均を下回った走行で終わらせない。
- 再走行の所要時間を測っておき、終了前の何回分を再走行に使えるかを決める。

## 7. 大きな binary は早めにファイルへ移す

新規アップロードの画像 bytes を DB からファイルへ移すと、DB と WAL への書き込みが減った。
一方、初期データの画像（約 180 万件、約 16 GB）を DB に残したまま終わった。終盤には、画像 bytes の読み出しが DB の IO 待ちの約 7 割、CPU のサンプルの約 4 分の 1 を占めていた。
初期データを DB host のファイルへ書き出し、Private ネットワーク越しに配る案は、検討しないまま終わった。効果は未検証である。

- 大きな binary の置き場所は序盤に決める。新規データだけでなく初期データも対象にする。
- 移す場合は、初期化と再起動後の取得経路、削除後の取得禁止などの仕様を同じ手順で確認する。

## 8. エージェントに任せるときの運用

- 改善案ごとに worktree と PR を分け、調整役が統合してから公式走行にかける。
- 公式走行中は、DB や負荷のかかるホストに解析クエリを流さない。解析クエリには `statement_timeout` を付ける。
- エージェントが利用上限で止まる前提で、走行・デプロイ・記録の手順を文書とスクリプトに残し、別のエージェントが引き継げるようにする。
- 外部の調査結果や subagent の報告を引用するときは、元の結論と前提（調べた範囲、使ったデータの時点）を確かめる。要約の段階で結論が変わることがあった。

## 9. 落とし穴の確認項目

- [ ] nginx の `worker_connections` は、プロキシ 1 要求で接続 2 本、SSE で開いたままの接続を数えて決める。既定の 768 で走行が打ち切られた。
- [ ] systemd の drop-in にある `EnvironmentFile` は、後に読まれる方が勝つ。env を変えたら `systemctl cat` と `/proc/<pid>/environ` で反映を確かめる。
- [ ] 競技時間内に全ホストを同時に再起動し、データの件数、レプリケーション、環境チェック、サービスの自動起動と再試行を確かめる。
- [ ] リポジトリに設定の控えを置くときは、運用文書で Git に入れないと決めた値を除く。
