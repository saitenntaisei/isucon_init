# ベンチ計測の欠測と混入を見分ける

[共通手順書](isucon-playbook.md) と [計測と並行処理](isucon-measurement-and-concurrency.md) を補う。
集計器の正常終了や公式得点の取得だけでは、性能比較に必要な観測がそろったとは限らない。
ここでは実験で起きたログ容量不足、観測区間のずれ、待ち行列による制御終了を一般化する。
新しい最適化を試す前に、比較できるデータがあるかを次の順で確認する。

## 1. ログ領域の容量と書き込みを確認する

RAM上のログ領域が満杯になり、ベンチは完走してもアクセスログが途中から残らない例があった。
候補側だけログを復旧すると、基準版の応答時間がなく、記録負荷の条件も変わる。
この状態で遅延の改善率を算出したり、得点差を変更だけの効果と扱ったりしない。

ベンチ投入前に次を確認する。

1. 実際の出力先mount、空きbytes、空きinode、rotation設定を調べる。
2. ログの最終時刻とsizeを控え、通常の確認要求で行が増えることを確かめる。
3. 設定したpathとprocessが開いているfileを照合する。rename後の旧inodeへ書いていないかも見る。
4. bufferのflush条件を確認し、初期化・負荷・終了処理を含む増加量を見積もる。
5. 計測後も末尾時刻、対象区間の件数、書き込みエラーを確認してから集計する。

容量は「現在の空きがある」だけで判断しない。
`必要容量 = 残す既存ログ + 1回の増加量 × 保存する回数 + 一時ファイル + 余裕` を目安にする。
得点上昇で要求数が増えるとログも増えるため、過去の増加量は上限ではない。
tmpfsの上限とホスト全体の空きメモリは別に監視する。
保存先がRAMでも、書式化・buffer管理・コピーのCPU費用は残る。

整理やrotationは走行の間に行い、必要な証拠を非公開領域へ退避する。
開いているログを削除しただけでは領域が解放されないことがあるため、サービスの正規のreopen手順を使う。
基準版と候補でログ設定や収集条件が変わったら、その差を記録して比較基準を取り直す。
基準版の遅延が欠測している場合、候補のp95が小さくても「前回より速い」とは結論しない。

## 2. 公式区間と観測区間を対応付ける

制御側が負荷開始を知ってから全ホストへmarkerを送ると、観測開始が負荷開始より遅れる。
終了markerにも配送遅延がある。marker間の集計を公式の全負荷区間と呼ばない。
両端を除いた区間は定常状態の比較には使えるが、開始直後や終了間際の動作は説明できない。

各artifactに次を残す。

| 項目 | 確認すること |
| --- | --- |
| 公式のphase時刻 | 初期化、負荷開始、負荷終了、最終検証の境界と時刻の取得元 |
| 観測時刻 | 各ホストの最初・最後のsample、markerの受信時刻、欠けた区間 |
| 時計の対応 | timezone、時刻補正の有無、時計差と配送遅延の不確かさ |
| 区間の被覆 | 全負荷を含むか、一部だけか、対応付けを確認できないか |
| 収集状態 | 終了コード、末尾レコード、欠測数、読取失敗数 |

時刻差が開始時と終了時で整合しない場合、単一のoffsetを仮定して全区間を覆ったとしない。
短いCPU profileの割合も、その採取区間の値として記す。
収集器が成功を返しても、公式区間の被覆が未確認なら「全負荷区間は未確認」と残す。

## 3. 累積差分にはprocessと世代の識別を付ける

CPU、process I/O、DB統計、cacheカウンタの差分は、同じ対象が継続していた場合だけ意味を持つ。
PIDだけでは再利用を見分けられない。開始・終了で次の識別情報を比較する。

- ホストのboot ID、PIDとprocessの開始時刻、実行binaryの識別。
- DB instanceや統計resetの境界、cacheの初期化世代。
- デバイス名だけでなくmajor:minorなどの識別と、カウンタの単位。

再起動やresetをまたいだ差分、負値、取得不能をゼロへ丸めない。
世代ごとに集計を分け、途中で終わったprocessや欠けたsampleを未捕捉として示す。
最初と最後のPID一覧だけでは、途中で起動して終了した短命processを数えられない。
アプリ以外の仕事を疑う場合は、必要な頻度の時系列やprocess生成・終了の観測を追加する。

## 4. 「ディスク書き込みゼロ」の観測範囲を限定する

DBやログをRAMへ移しても、journal、管理接続、OS処理などが書き込む場合がある。
tmpfsのpageもswapへ退避され得る。配置先だけで物理ディスクへの書き込みがないとは判断しない。

| 観測 | 説明できることと限界 |
| --- | --- |
| `/proc/PID/io` | processのI/O会計。`write_bytes`や`cancelled_write_bytes`はデバイスの書込量と一対一には対応しない |
| block deviceの統計 | そのdeviceに発行された書込量。partitionと親deviceを足すと二重計上し得る |
| iowait | CPU時間の分類。ゼロに近くても書込がないとは限らない |
| ファイルのsizeやmtime | ファイルの変化。flush済みか、別pathで書いたかは分からない |

対象mountの背後にあるdeviceとswapを特定し、同じ区間のdevice統計とprocess統計を突き合わせる。
OSから見たdevice統計は、記憶装置内部の実際の媒体書込量とは区別する。
全区間を覆えない場合は「観測した区間での値」と報告する。
負荷前後を含む非ゼロの差分から、負荷中だけの書込量を確定しない。

## 5. バックグラウンド処理とjobの生存を分けて扱う

自動パッケージ更新が走行中にCPUとI/Oを使い、RAM化の比較へ混入した例がある。
投入前に更新処理などの稼働状況を確認し、実行中なら完了を待って比較条件をそろえる。
計画してtimerを一時停止する場合は元の状態と復元手順を記録し、走行後に復元を確認する。
timer停止だけでは既に走る更新処理は終了しない。package管理処理を強制終了して条件を作らない。
更新によってpackageやkernelが変わった場合は、その環境差も記録する。

ポータルの待ち行列が長いと、制御スクリプトが終了してもjobは待機・実行を続ける場合がある。
投入直後にjob IDを保存し、ローカルtimeout後も同じjobの公式状態と結果を確認する。
投入応答を失った場合も、履歴や識別labelで受付済みかを確認してから次の操作を決める。
ローカルのtimeoutをjob中断と見なして自動再投入しない。
observerが先に止まった回は、得点を回収できてもCPUやSQLの比較データがないと記す。

最後に「公式結果」「観測の被覆」「比較条件の一致」を別々に判定する。
公式PASSは、その回の検査を通った結果であり、欠測の補完や仕様遵守全体の証明にはならない。
不足した観測を仮説で埋めず、どの結論まで出せるかを実験記録に残す。
